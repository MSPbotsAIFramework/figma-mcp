## Product design

### Goals / non-goals

**Goals** (v1, first version of the connector):
- Let an agent identify which Figma account/token it is talking to.
- Let an agent find a team's projects (folders) and the files inside them.
- Let an agent read a file's design structure (the node tree), a scoped subset of nodes, and lightweight file metadata (name, thumbnail, last-modified) without pulling the whole tree.
- Let an agent render specific nodes to image URLs (PNG/JPG/SVG/PDF) and list the download URLs of a file's embedded image fills.
- Let an agent read a file's version history.
- Let an agent read, post, and delete comments on a file, on explicit user request.

**Non-goals (v1)**:
- Editing design content (moving/resizing/restyling nodes, adding layers). Figma's public REST API does not support this at all — content edits are only possible through the Figma Plugin API, which runs inside the Figma app, not over HTTP. No REST endpoint exists to wrap, so this stays out of scope indefinitely, not just for v1.
- Design system / library management (publish or read team components, styles, variables), team/member administration, activity logs, developer logs, AI usage, payments, SCIM, webhooks, dev resources. See "Decisions made by DEV01" for why each is deferred.
- OAuth2 app registration (multi-tenant consent flow). v1 authenticates with a user's own personal access token.

### Acceptance criteria

- **AC1** — Given a valid `X-Figma-Token`, `figma_get_me` returns the authenticated user's id, email, and handle.
- **AC2** — Given a request to any tool without `X-Figma-Token`, the server returns HTTP 401 with a body listing the required header.
- **AC3** — Given a file key, `figma_get_file` returns the file's node tree; an optional `ids` filter scopes it to specific nodes/subtrees and an optional `depth` limits how far the tree is walked.
- **AC4** — Given a file key and a list of node ids, `figma_get_file_nodes` returns only those nodes (and their subtrees), not the whole file.
- **AC5** — Given a file key, `figma_get_file_meta` returns name, thumbnail URL, and last-modified time without the node tree.
- **AC6** — Given a file key and node ids, `figma_render_images` returns rendered image URLs in the requested format (`png`/`jpg`/`svg`/`pdf`) and scale.
- **AC7** — Given a file key, `figma_list_image_fills` returns the download URLs of the file's embedded image fills, keyed by image reference.
- **AC8** — Given a file key, `figma_list_file_versions` returns the version history as a page of versions plus opaque `prev_page`/`next_page` cursors.
- **AC9** — Given a team id, `figma_list_folders` returns that team's top-level folders; given a folder id instead, it returns that folder's direct subfolders. Exactly one of the two must be given.
- **AC10** — Given a folder id, `figma_list_folder_files` returns the files directly inside that folder.
- **AC11** — Given a file key, `figma_list_comments` returns the file's existing comments (author, message, position metadata, timestamps).
- **AC12** — Given a file key and a message, `figma_create_comment` posts a new comment (optionally as a reply via `comment_id`, or anchored to a position via `client_meta`). The tool description says this runs only on explicit user request.
- **AC13** — Given a file key and a comment id with `confirm: true`, `figma_delete_comment` permanently deletes that comment; without `confirm: true` it returns a "not done, confirm first" result and makes no API call.
- **AC14** — Given the upstream Figma API returns 400 / 403 / 404 / 429 / 5xx / a network error, every tool returns the structured error envelope `{"error":{"code","message","retryable"}}` with the code from the fixed vocabulary — never raises an exception to the caller.
- **AC15** — Every list tool caps its page size (default ≤ 50, hard max ≤ 200) and its serialized result at 20000 characters, and reports `has_more` / continuation fields when a page was cut.
- **AC16** — The raw `X-Figma-Token` value never appears in logs, error messages, or tracebacks.
- **AC17** — Two concurrent requests carrying different tokens never see each other's credentials or data (per-request isolation, no shared mutable state between tenants).

## Tech design

### Conclusion

Build `figma-mcp` from scratch (vendor-mcp-development main line A) against Figma's public REST API (`https://developers.figma.com/docs/rest-api/`), authenticating with a personal access token carried in the `X-Figma-Token` header on every request. 12 tools across 6 capability groups (identity, file content, file metadata, images, versions, folders, comments). No gateway change needed (not a builtin-OAuth vendor, see "Current state").

### Where the current implementation lives

Nothing: `MSPbotsAIFramework/figma-mcp@main (0f469f4)` is a one-commit README scaffold with no `src/`. This document describes the first version to be implemented in the dev leg.

### Option analysis

- **REST API with personal access token (chosen)** vs. **OAuth2 app**: Figma supports both. A personal access token needs no app registration, no redirect URI, and no consent-screen hosting — the account owner generates one token in their own Figma settings and pastes it into the MSPbots Connector UI, the same "bring your own API key" flow as Hudu/Box's non-OAuth paths. An OAuth2 app would let MSPbots broker consent without the user ever seeing a raw token, which is nicer UX, but requires registering a Figma OAuth app, hosting a callback, and doing token refresh — a materially bigger first version for a ticket that names no specific need. Deferred; see "Decisions made by DEV01."
- **v1 teams/projects endpoints** vs. **v2 folders endpoints**: Figma's own docs mark `GET /v1/teams/:team_id/projects` and `GET /v1/projects/:project_id/files` "Deprecated. Use `GET /v2/.../folders` instead." Building a new connector on a documented-deprecated endpoint would mean next-day rework; v2 folders endpoints are used instead (AC9/AC10).
- **Mirror every endpoint 1:1** vs. **cover capability groups and cut library/admin/webhook endpoints**: rejected 1:1 mirroring — SOP §2 caps a service at ≤ 20 tools and asks for "capabilities not endpoint mirrors." Figma's endpoint surface (file duplication, team/folder writes, variables, library components/styles, webhooks, activity/developer logs, AI usage, payments, SCIM) is large and mostly Enterprise-plan-gated or administrative; see "Decisions made by DEV01" for the per-group reasoning.

### Data & API contract

**Credential header** (declared in README, read verbatim in `server.py`):

| Header | Required | Meaning |
|---|---|---|
| `X-Figma-Token` | yes | Figma personal access token (Settings → Personal access tokens in the Figma web app). Scopes needed: `current_user:read`, `file_content:read`, `file_metadata:read`, `file_versions:read`, `folders:read`, `file_comments:read`, `file_comments:write`. |

Missing header → `401 {"error":"Missing credentials","message":"Missing header(s): X-Figma-Token","required_headers":["X-Figma-Token"]}` (AC2), same envelope shape as `hudu_mcp`'s `GatewayCredentialsMiddleware`.

**Tools** (name · annotation · upstream endpoint · key params → result):

| Tool | Annotation | Endpoint | Params | Result |
|---|---|---|---|---|
| `figma_get_me` | READ_ONLY | `GET /v1/me` | — | `{id, email, handle, img_url}` |
| `figma_get_file` | READ_ONLY | `GET /v1/files/:key` | `file_key`, `ids?`, `depth?`, `geometry?` | `{name, document, components, styles, lastModified, thumbnailUrl, version}` (long fields capped per AC15) |
| `figma_get_file_nodes` | READ_ONLY | `GET /v1/files/:key/nodes` | `file_key`, `ids` (required, ≥1) | `{nodes: {<id>: {document, components, styles}}}` |
| `figma_get_file_meta` | READ_ONLY | `GET /v1/files/:key/meta` | `file_key` | `{name, thumbnail_url, last_modified, ...}` — no node tree |
| `figma_render_images` | READ_ONLY | `GET /v1/images/:key` | `file_key`, `ids` (required), `format?` (png\|jpg\|svg\|pdf, default png), `scale?` (1–4) | `{images: {<node_id>: <url or null>}, err?}` |
| `figma_list_image_fills` | READ_ONLY | `GET /v1/files/:key/images` | `file_key` | `{images: {<image_ref>: <url>}}` |
| `figma_list_file_versions` | READ_ONLY | `GET /v1/files/:key/versions` | `file_key`, `cursor?` (opaque, from a previous call's `next_page`) | `{versions: [...], prev_page, next_page}` (AC8) |
| `figma_list_folders` | READ_ONLY | `GET /v2/teams/:team_id/folders` or `GET /v2/folders/:folder_id/folders` | exactly one of `team_id` / `folder_id` (AC9) | `{folders: [...]}` |
| `figma_list_folder_files` | READ_ONLY | `GET /v2/folders/:folder_id/files` | `folder_id`, `branch_data?` | `{files: [...]}` |
| `figma_list_comments` | READ_ONLY | `GET /v1/files/:key/comments` | `file_key` | `{comments: [...]}` |
| `figma_create_comment` | WRITES | `POST /v1/files/:file_key/comments` | `file_key`, `message`, `comment_id?` (reply to), `client_meta?` (anchor position) | the created comment object |
| `figma_delete_comment` | DESTRUCTIVE | `DELETE /v1/files/:file_key/comments/:comment_id` | `file_key`, `comment_id`, `confirm` (must be `true`, AC13) | `{done: true, deleted_comment_id}` or a not-confirmed result |

**Pagination**: `figma_list_file_versions` passes Figma's own opaque `prev_page`/`next_page` cursor strings straight through as a `cursor` input and `prev_page`/`next_page` outputs — not an offset model, because Figma's cursors are not guaranteed to be offsets. List-of-folders/files/comments/image-fills endpoints are not cursor-paginated upstream (Figma returns the full set); this server still caps the serialized result at 20000 chars per AC15 using the shared `dump_json_capped` truncation (same mechanism as `hudu_mcp/_json.py`), which degrades gracefully (shortens long fields, then cuts the list and reports `has_more`/`truncated`) rather than ever dropping output silently.

**Backward compatibility**: not applicable — new repo, no existing callers.

### Key flow / sequence

1. Gateway receives a tool call from an agent, resolves the tenant's stored Figma PAT, and forwards the HTTP request to `figma-mcp` with `X-Figma-Token` set.
2. `GatewayCredentialsMiddleware` reads the header; missing → 401 (ends here). Present → sets `FigmaCredentials` on a `contextvars.ContextVar` for the duration of this request.
3. The called tool builds a `FigmaClient` from the context var and calls the matching Figma REST endpoint.
4. `FigmaClient.request()` retries once or twice on `429`/`5xx`/network error (GET only; a POST/DELETE is never retried so a comment is never double-posted/double-deleted), honoring `Retry-After`.
5. On success, the tool shapes the response into the table above and returns it through `dump_json_capped`. On failure, `run_tool()` catches `FigmaError`/`ValueError`/any other exception and returns the structured error envelope — the caller never sees a traceback (AC14).
6. `finally` in the middleware resets the context var so the next request (possibly a different tenant, since the container is shared) starts clean (AC17).

### Non-functional

- **Idempotency / concurrency**: reads are naturally idempotent and safely retried; `figma_create_comment` (POST) and `figma_delete_comment` (DELETE) are never retried by the client on failure — if the call times out mid-flight the tool returns `upstream_error` and lets the agent decide whether to re-ask the user, rather than risk a duplicate comment or an unintended second delete attempt (which would just 404 harmlessly, but we don't rely on that).
- **Performance**: `_CALL_BUDGET_SECONDS = 100` (under the gateway's 120s tool-call timeout, same margin as `hudu_mcp`). `figma_get_file` without `ids`/`depth` can return a very large tree for a complex file; the tool description tells the agent to prefer `figma_get_file_nodes`/`figma_get_file_meta` when it only needs part of a file, and `dump_json_capped` prevents an oversized response from ever being returned whole.
- **Security**: `X-Figma-Token` is read once per request from the header, stored only in a per-request `contextvars.ContextVar`, never logged or echoed in error messages (`FigmaCredentials.__repr__` redacts it, mirroring `HuduCredentials`), never persisted to disk or environment. No cookies are sent or stored (shared `httpx.AsyncClient` uses a reject-all cookie jar, same as `hudu_mcp`) since the HTTP client is shared across tenants in one process.
- **Multi-tenant isolation**: one process serves every tenant; nothing about a request (token, response data) is cached or stored outside that request's `contextvars.ContextVar`, so two concurrent calls with two tenants' tokens cannot see each other's data (AC17). No module-level or global mutable state holds credentials or results.
- **Observability**: each upstream call logs method/path/status/duration/attempt (no token, no response body) at INFO; unexpected exceptions log at WARNING with the exception type only — same logging contract as `hudu_mcp/api_client.py:153-157` and `tools/_common.py:140-147`.

### Effort & breakdown

Story points: 3

Tier guide (`templates-design.md` "How to size a Story Point"): a brand-new MCP repo against a previously-unbuilt, fully-public vendor API is "new subsystem" work — the same tier as the three most recent precedents in this org (Hudu, Box, Plaid), all scoped single-vendor connectors with roughly a dozen tools and no multi-tenant credential wrinkles beyond the standard header pattern. Considerations:
- New repo, new vendor, external API never before integrated in this org → pushes above 1–2.

- No data migration, no cross-repo dependency, no UI surface, no destructive-by-default operations beyond one confirm-gated comment delete → keeps it from climbing further.

### Risks & dependencies

- **Risk**: Figma's documented rate limits vary by the caller's plan tier and seat type (Starter/Professional/Organization/Enterprise × Dev-Full/View-Collab), which this server cannot know in advance. Mitigated by keying retry/backoff off the live `429` + `Retry-After` response rather than a hardcoded budget (same approach as every other MCP in this org).
- **Risk**: `figma_get_file` on a large/complex file can be slow or return a very large payload upstream. Mitigated by `ids`/`depth` filters and `dump_json_capped`; not a correctness risk, a UX one documented in the tool description.
- **Dependency**: none on another ticket or repo. Self-contained, single-repo change.
- **Dependency (soft)**: v1 assumes a Starter-or-above Figma plan is enough for every chosen endpoint. None of the 12 tools touch an endpoint whose scope list says "Enterprise plan only" (`current_user:read`, `file_content:read`, `file_metadata:read`, `file_versions:read`, `folders:read`, `file_comments:*` are all unannotated/generally available) — confirmed against the scope table fetched from `developers.figma.com/docs/rest-api/scopes/` on 2026-11-02.

### Decisions made by DEV01

(Posted verbatim in a separate `[DESIGN DECISIONS]` comment per `mcp-track.md` §2.4.)

- **Personal access token over OAuth2 app** — simplest self-service credential for v1; no Figma OAuth app registration, redirect URI, or token-refresh logic needed. Alternative not chosen: register a Figma OAuth2 app for a brokered consent flow (bigger first version, no ticket requirement calling for it).
- **v2 folders endpoints over v1 teams/projects endpoints** — Figma's own docs mark the v1 pair deprecated in favor of `GET /v2/teams/:team_id/folders` and `GET /v2/folders/:folder_id/files`. Alternative not chosen: build on the documented-deprecated v1 pair (would need redoing immediately).
- **Excluded Variables (`file_variables:*`)** — scope table marks both read and write "Enterprise plan only"; not guaranteed available to a self-service PAT user. Alternative not chosen: build it and let it 403 for non-Enterprise tenants (adds a tool nobody can reliably use).
- **Excluded team/file library content (`library_content:read`, `team_library_content:read`, `library_assets:read`) and `library_analytics`** — published-component/style browsing is a design-system feature not implied by the ticket's generic "connect Figma" ask, and `library_analytics:read` is explicitly Enterprise-only. Alternative not chosen: include them in v1 (scope creep beyond what any comment on this ticket asked for; can be added as a follow-up main-line-B ticket if someone asks for design-system browsing specifically).
- **Excluded webhooks** — creating a Figma webhook requires giving Figma a public callback URL to push events to; this server has no public endpoint of its own to receive them (same reasoning as every other poll-only MCP in this org, e.g. Hudu). Alternative not chosen: expose `figma_create_webhook` pointed at a URL the caller supplies (the server would never see the resulting events, so the tool would be useless on its own).
- **Excluded activity logs, developer logs, AI usage, payments, SCIM, team/member writes, file duplication, folder/team writes** — all are either Enterprise-plan-and-org-admin-gated, or organization-administration features orthogonal to "an agent reading/commenting on designs." Alternative not chosen: build them (out of scope for a per-tenant design-review connector; also most need a private OAuth app per the scope table, which v1 does not have).
- **`figma_list_folders` takes `team_id` OR `folder_id` rather than two separate tools** — Figma exposes "top-level folders of a team" and "subfolders of a folder" as two endpoints; folding them into one tool with mutually-exclusive optional args keeps the tool count down (SOP §2's "capabilities not endpoint mirrors") without losing either capability.
- **No base-URL header** — unlike Hudu (self-hosted per instance), Figma's REST API has one fixed host (`api.figma.com`); hardcoding it removes a whole class of misconfiguration (typo'd base URL) that Hudu's connector has to guard against. Figma for Government's different host is a documented edge case with no signal in this ticket that it applies; tracked as Open Question Q2, not built.
- **`confirm: true` required on `figma_delete_comment`** — matches this org's convention for any permanent delete (e.g. `hudu_delete_company`), even though a single comment is lower-blast-radius than a company record; consistency with the rest of the fleet was judged more valuable than skipping the gate for a "small" delete.

### Live verification (real HTTP, real upstream calls to `api.figma.com`; no account configured, so a placeholder token is used)

1. `GET /health` → `200 {"status":"ok"}`.
2. `POST /mcp tools/list` with no `X-Figma-Token` → `401 {"error":"Missing credentials","message":"Missing header(s): X-Figma-Token","required_headers":["X-Figma-Token"]}` (AC2, TC-FIGMA-002 confirmed live in addition to the automated test).
3. `POST /mcp tools/list` with `X-Figma-Token: figd_placeholder-token` → `200`, all 12 tool names present (`figma_get_me`, `figma_get_file`, `figma_get_file_nodes`, `figma_get_file_meta`, `figma_render_images`, `figma_list_image_fills`, `figma_list_file_versions`, `figma_list_folders`, `figma_list_folder_files`, `figma_list_comments`, `figma_create_comment`, `figma_delete_comment`).
4. `POST /mcp tools/call figma_get_me {}` with the placeholder token → **real call to `https://api.figma.com/v1/me`, which answered `401 Unauthorized`** (not the `403` the tech design's `_STATUS_TO_CODE` table assumed from Figma's documentation). Before the fix this came back as `invalid_argument` (wrong: the status map had no `401` entry and fell through to the generic ≥400 bucket); fixed by adding `401 → ("unauthorized", False)` to `_STATUS_TO_CODE` in `api_client.py` (commit `aab40c1`), and the envelope now reads `{"error":{"code":"unauthorized","message":"Figma returned HTTP 401 for me: Invalid token","retryable":false}}` — no exception escaped either time (AC14). Also updated `tests/test_api_client.py::test_status_to_code_mapping` to cover `401`.
5. `POST /mcp tools/call figma_list_folders {}` (neither `team_id` nor `folder_id`) → `{"error":{"code":"invalid_argument","message":"Give exactly one of team_id or folder_id, not both and not neither.","retryable":false}}`, and the mock-transport test confirms no upstream call is made either (TC-FIGMA-011/AC9).
6. `POST /mcp tools/call figma_get_file_meta {"file_key":"ZZZZZZZZZZZZZZZZZZZZZZ"}` with the placeholder token → also `401 unauthorized` (the bad token is rejected before Figma would check whether the file key exists), confirming the error path is identical across tools and never raises. TC-FIGMA-018 (a real 404-on-invalid-file-key, which needs a *valid* token to reach) is therefore still "not run: needs a real vendor account" — a placeholder token cannot get far enough upstream to exercise it.
